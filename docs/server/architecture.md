### Architecture

In this document, we will discuss the architecture of this backend service from
the bottom up. Developers should follow all the rules and guidelines defined
here throughout development.

If you are unfamiliar with how Spring Boot, the primary framework we use in this
workspace, works, please read [this post][java-web-project] first.

Regarding layers, we will first discuss how the backend service communicates
with the database through the persistence layer. Then, we will elaborate on how
the data in the persistence layer is exposed to the business-logic layer (BLL),
where we encapsulate common business logic in functions for higher layers to
use. Finally, we will thoroughly discuss how controller methods handle incoming
requests and send responses back to clients.

We will also introduce a set of rules for configurations, exceptions, models,
logging, and tests to ensure consistency across the project and improve the
readability and maintainability of the codebase.

#### Database and Persistence Layer

We use [PostgreSQL][postgres], a free and open-source relational database
management system (DBMS), to store data in this project.

We use [JPA (Jakarta Persistence)][jpa] to manage [object-relational mapping
(ORM)][orm] between the relational database and Java objects.

Don't worry if these terms feel unfamiliar. Let's take a look at a simple class,
`com.naisa.model.entity.Client`:

```java
@JavaBean
@Entity(name = "client")
public class Client {
  @Id
  @GeneratedValue(strategy = GenerationType.IDENTITY)
  @Column(name = "id", nullable = false, updatable = false)
  private Long id;

  @Generated(event = EventType.INSERT)
  @ColumnDefault("gen_random_uuid()::text")
  @Column(name = "api_key", length = 36, nullable = false)
  @Size(max = 36, message = "API key must not exceed 36 characters")
  private String apiKey;

  public Long getId() {
    return id;
  }

  public void setId(final Long id) {
    this.id = id;
  }

  public String getApiKey() {
    return apiKey;
  }

  public void setApiKey(final String apiKey) {
    this.apiKey = apiKey;
  }
}
```

If we ignore all the annotations (those that start with `@`), this class
basically contains two fields—`id` and `apiKey`—and two pairs of corresponding
getters and setters.

A public class with private fields and corresponding getters and setters follows
the [JavaBean][java-bean] convention. Apparently `Client` follows this
convention, so it is marked with a `@JavaBean` annotation, which has no
functional effect.

The `@Entity` annotation tells [Hibernate][hibernate], an ORM framework, that
this class represents a persistent entity. The `name` attribute sets the entity
name to "client". In a relational database, an entity represents a single row
(record) within a table. Classes that are annotated with `@Entity` are referred
to as **entity classes**.

The annotations on the two fields provide Hibernate with additional information
about the corresponding columns beyond their types, or specify validation
constraints:

1. `@Id`: the field maps to the primary key column.
2. `@GeneratedValue(strategy = GenerationType.IDENTITY)`: the database generates
   the identifier using an identity column.
3. `@Column(name = "id", nullable = false, updatable = false)`: the column is
   named "id", cannot contain null values, and is excluded from updates
   generated by Hibernate.
4. `@Size(max = 36, message = "API key must not exceed 36 characters")`: this
   annotation specifies a validation constraint for the field, which we will
   discuss later.

When the service starts, if Hibernate doesn't find the `client` table in the
database, it will create it by executing the following SQL statement:

```sql
CREATE TABLE client (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    api_key VARCHAR(36) NOT NULL DEFAULT gen_random_uuid()::text
);
```

> [!NOTE]
>
> Hibernate automatically creates missing relations (tables) because the
> property `spring.jpa.hibernate.ddl-auto` is set to `update`. The property
> defaults to `none`.

Now that the table is set up, we need a way to manipulate its data.
`com.naisa.repository.ClientRepository` is defined like this:

```java
@Repository
public interface ClientRepository extends JpaRepository<Client, Long> {
  @Nullable
  Client findClientByApiKey(String apiKey);
}
```

This is a typical Spring Data JPA repository. The two type arguments of
`JpaRepository` (in our case, `Client` and `Long`) represent the entity class
and the type of its primary key, respectively. A JPA repository is defined as an
interface, so the methods shown here have no implementation. Spring Data JPA
creates the repository implementations during Spring application startup.

If Spring Data JPA can infer what a method does from its name, it will generate
an implementation for it. For example, `findClientByApiKey(String apiKey)`
matches the pattern `findXByY`, where `X` describes the entity and `Y`
identifies a field. Therefore, Spring Data JPA will generate an implementation
that executes a SQL statement like this:

```sql
SELECT * FROM client WHERE api_key = ?
```

This feature is referred to as **query creation**. [This
document][jpa-query-keywords] lists all the supported keywords.

However, some repository methods involve complex logic, making them difficult or
impossible to define using the keywords supported by Spring Data JPA. In these
cases, we can write the SQL ourselves. Below is an example of using the `@Query`
annotation to specify a SQL statement. This is a hypothetical example: the
current codebase does not define `User`, `users`, `orders`, or this repository
method.

```java
@Query(value = """
  SELECT u.*
  FROM users u
  WHERE u.status = :status
    AND EXISTS (
      SELECT 1
      FROM orders o
      WHERE o.user_id = u.id
        AND o.total > :minTotal
    )
""", nativeQuery = true)
List<User> findUsersWithLargeOrders(
  @Param("status") String status,
  @Param("minTotal") BigDecimal minTotal
);
```

By setting `nativeQuery = true`, we tell Spring Data JPA that the given
statement uses native SQL rather than JPQL. In this project, we use PostgreSQL
as our only relational database, so for simplicity, we set `nativeQuery = true`
for all `@Query` annotations.

#### Business-logic Layer

Business logic is defined in the business-logic layer (BLL), also called the
**service layer** in Spring Boot projects. Being agnostic to how data are stored
specifically, the BLL should always use repositories to manipulate data. In
other words, direct communication with databases (or other data stores) is
prohibited in this layer.

**Service classes** reside in the `com.naisa.service` package, and they should
be annotated with `@Service`. For example:

```java
@Service
public final class ClientService {
  private final ClientRepository clientRepository;

  private ClientService(final ClientRepository clientRepository) {
    this.clientRepository = clientRepository;
  }

  @NotNull
  public Client getClientByApiKey(final String apiKey) {
    final Client client = this.clientRepository.findClientByApiKey(apiKey);
    if (client == null) {
      throw ClientException.INVALID_API_KEY.clone();
    }

    return client;
  }

  // other methods...
}
```

Here, the field `clientRepository` is wired up by Spring through the
constructor. Service classes should be self-contained.

In service methods, **service exceptions** are thrown in the situations where
the data violate some business-logic rules. For example, in `getClientByApiKey`,
the business logic expects a client associated with the given API key to exist.
Therefore, when this rule is violated (i.e., client is null), we throw a service
exception (in this case, `ClientException.INVALID_API_KEY.clone()`), which will
be discussed in the upcoming sections.

#### Controller Layer

A decade ago, the [MVC architectural pattern][mvc] was a hit. But later, people
shifted to frontend-backend separation, where Spring services return JSON
instead of complete web pages. In MVC, controller methods usually return view
names. But in a decoupled backend, controller methods return objects, which are
serialized into the HTTP response body.

So, if you're wondering what `@RestController` does here, it basically tells
Spring that the return values of controller methods in this class should be
written to the HTTP response body, as JSON in this project, instead of being
treated as view names.

```java
@RestController
@RequestMapping("/v1/clients")
public class ClientController {
  private final ClientService clientService;

  public ClientController(final ClientService clientService) {
    this.clientService = clientService;
  }

  @PostMapping
  public ResponseEntity<Capsule<Client>> issueApiKey() {
    final Client createdClient = clientService.createClient();
    return ResponseEntity.status(HttpStatus.CREATED)
        .body(new Capsule<>("API key has been issued.", createdClient));
  }
}
```

**Controller classes** reside in `com.naisa.controller`. Because we are using a
[RESTful API][rest-api] in this project, we include an API version by
convention. Controller classes for version 1 therefore reside in
`com.naisa.controller.v1`. Also, the path in `@RequestMapping` should start with
`/v1`.

Upon receiving an HTTP request, Spring Boot first parses it into an
`HttpServletRequest` object, then matches the path against registered controller
methods. For example, `issueApiKey` in `ClientController` is annotated with
`@PostMapping`, so it is registered as a valid controller method at startup. The
path pattern associated with the controller method is `/v1/clients`, which is
obtained by combining the value in `@RequestMapping` with the value in
`@PostMapping`. In our case, `@PostMapping` has an empty value, so the resulting
path pattern is still `/v1/clients`. Read [this document][uri-patterns] to learn
more about this.

Make sure that no patterns end with a slash (`/`).

##### Capsule

Controller methods in this project return `ResponseEntity<Capsule<T>>`, where
`T` is the payload type (for example, `Client` or `Object`). `ResponseEntity` is
provided by Spring Framework. It serves as a utility wrapper that allows
developers to neatly set the HTTP status code and response body. `Capsule`
(presented in `com.naisa.common`) is a proposed Java bean that defines the
structure of the JSON object in the response body.

The client should expect a consistent JSON structure in the response body, as
follows:

```json
{
    "message": "<Brief message to help clients understand the result of the request.>",
    "data": {
        "foo": "bar"
    },
    "errorCode": "error_code"
}
```

An **error response** must contain the `errorCode` field, while a **successful
response** must not. The `data` field is optional for both response types.
`Capsule` uses `@JsonInclude(JsonInclude.Include.NON_NULL)` to omit fields whose
values are null. The health endpoint returns HTTP 204 (No Content), so clients
should not expect a JSON body from it.

#### Configurations

**Configuration classes** reside in `com.naisa.config`, and each is
well-defined. In a Spring Boot project, configuration files are usually
properties files in `src/main/resources`. At startup, Spring Boot reads
properties from `application.properties` and any other specified properties
files (`DatabaseConfiguration` is a typical example).

#### Exceptions

**Exception classes** reside in `com.naisa.exception`. Every class except
`ServiceException` itself must be final and extend `ServiceException`. Every
exception class contains a set of static final instances of itself. The names of
these instances should be in SCREAMING_SNAKE_CASE.

Exception instances in these classes are called **service exceptions**. As the
name suggests, they must only be thrown in the service layer. Controller methods
can catch these exceptions and build responses accordingly.

Service exception constructors take three required parameters and one optional
parameter:

- `code`: the error code to set using `Capsule::setErrorCode()`.
- `message`: the error message to set using `Capsule::setMessage()`.
- `status`: the HTTP response status code.
- `cause`: the error that caused this exception.

`ServiceException` implements `Cloneable`. Always use `clone()` to throw a new
exception instance instead of throwing one of the shared static exception
instances defined in other exception classes. If the service exception has a
cause, use `causedBy()` to create a new exception with the specified cause.

#### Controller Advice

The `com.naisa.controller.GlobalExceptionHandler` class defines exception
handlers, each implemented as a method. If a service exception is thrown in the
service layer but isn't caught in the controller layer, it will be handled by
`handleServiceException`, which sets the HTTP status to the exception's `status`
and uses the result of `Capsule.fromServiceException` as the response body
object.

The `handleUnreadableBody` handler maps `HttpMessageNotReadableException` to
HTTP 400 with error code `request.invalid_body`. The `handleValidationFailure`
handler maps `MethodArgumentNotValidException` to HTTP 400 with error code
`request.validation_failed`.

Other exceptions reaching this advice are handled by
`handleUnexpectedException`, which logs the exception and returns HTTP 500 with
error code `server.internal_error`. This fallback currently also covers request
errors for which no more specific handler has been defined.

This class is very important, and it is worth reading its source code carefully.

#### Interceptors

Interceptors reside in `com.naisa.interceptor` and should all be registered in
`WebConfiguration`, as mentioned earlier. An interceptor is a class that
implements `HandlerInterceptor` and overrides one of the declared methods. The
`preHandle` method, for example, is invoked before the controller method handles
the request. [This document][handler-interceptor] introduces how an interceptor
works in detail.

The `LoggingInterceptor` creates INFO log entries before and after the request
is handled by the controller method. In both entries, it includes the HTTP
method and the request path. In the first entry, it also includes which
controller method handles it; in the second entry, it also includes the response
time measured between `preHandle` and `postHandle`. The second log entry is
produced only when `postHandle` runs; it is skipped when an interceptor stops
the request or the handler throws an exception.

The `AuthorizationInterceptor` verifies user authorization when required. It
checks controller methods annotated with `@AuthorizationRequired` (defined in
`com.naisa.common.annotation`).

```text
POST /v1/clients handled by ClientController:issueApiKey
POST /v1/clients handled in 55 milliseconds
```

#### Models

In this project, models refer to JavaBean classes that are specific to a
particular operation and used in the controller, service, and repository layers.
Model types include the aforementioned entities, DTOs (data transfer objects),
and VOs (view objects). DTOs are used to transfer data between the controller
and service layers, while VOs define the data in API responses.

Model classes should be placed in the `com.naisa.model` package.

#### Logging

The Spring Boot framework already provides a [logging
system][spring-boot-logging]. Define a private static final logger
(`org.slf4j.Logger`) at the beginning of any class in which you want to log
something, for example:

```java
private static final Logger LOGGER = LoggerFactory.getLogger(MyClass.class);
```

Replace `MyClass.class` with the actual class name followed by `.class`.
